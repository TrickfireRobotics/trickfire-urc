---
title: Connecting to the Simulator
description: Bridge ROS 2 topics between the Gazebo simulator and the trickfire-urc container.
---

The simulator ([gazebo-simulations](https://docs.trickfirerobotics.com/simulations)) runs either natively through pixi or in its own Docker container. This repository always runs in a Docker container. ROS 2 discovers nodes over DDS multicast, and multicast can't cross the Docker boundary, so neither side can see the other's topics by default.

To fix that, one [zenoh bridge](https://github.com/eclipse-zenoh/zenoh-plugin-ros2dds) runs next to each side. Each bridge discovers its local ROS 2 graph normally and forwards topics, services and actions to the other bridge over a single TCP port (`7447`, bound to `127.0.0.1` only). Neither repository's RMW or packages change.

```text
 sim (native or container)                              trickfire-urc (Docker)
 Gazebo ─DDS─ sim-side bridge ── tcp 127.0.0.1:7447 ──► sim-bridge service ─DDS─ robot
```

## Which mode to use

| How the sim runs                                 | OS                   | Sim-side bridge                  |
| ------------------------------------------------ | -------------------- | -------------------------------- |
| Native with `pixi run sim ...`                   | macOS, Linux, WSL2   | `.devcontainer/sim-bridge.sh native` |
| In its devcontainer (`simulations` container)    | Windows, macOS       | `.devcontainer/sim-bridge.sh docker` |
| In its devcontainer on Linux Docker Engine       | Linux                | `native` is recommended instead (see troubleshooting) |

## Steps

<Callout type="warn" title="Host terminal, not the devcontainer">
    `sim-bridge.sh` runs on the **host** (a regular terminal on your machine, outside VS Code's
    devcontainer terminal). The sim-side bridge has to see the sim's traffic, and the devcontainer
    has no Docker access. Running it inside the devcontainer exits with an error.
</Callout>

1. Start the simulator as usual, e.g. `pixi run sim gazebo chassis`.
2. Open this repository in its devcontainer. The urc-side bridge (`sim-bridge` service) starts with it automatically.
3. In a **host** terminal, from this repository's root, start the sim-side bridge and leave it running:

    ```bash title="Host terminal"
    .devcontainer/sim-bridge.sh native   # or: docker
    ```

4. In the devcontainer, the sim's topics are now available:

    ```bash title="Devcontainer"
    ros2 topic list
    ros2 topic echo /clock --once
    ```

If the devcontainer was created before the `sim-bridge` service existed, run **Dev Containers: Rebuild Container**, or start the service once with `.devcontainer/sim-bridge.sh up` from a host terminal. The first `native` run downloads the bridge (~20 MB) into `~/.cache/trickfire/`.

<Callout type="note" title="Windows without WSL">
    `sim-bridge.sh` works from Git Bash. From PowerShell, run the sim-side bridge directly (and the first line only if the `sim-bridge` service isn't running):

    ```powershell
    docker compose -p trickfire-urc_devcontainer -f .devcontainer/docker-compose.yml up -d sim-bridge
    docker run --rm -it --network container:simulations -e ROS_DISTRO=jazzy eclipse/zenoh-bridge-ros2dds:1.10.1 client -e tcp/host.docker.internal:7447 --no-multicast-scouting
    ```

    Check the project name with `docker inspect -f "{{index .Config.Labels \"com.docker.compose.project\"}}" trickfire-urc`.
</Callout>

## Limits

Only topics that someone subscribes to on the other side are forwarded. Control, odometry, TF, GPS and `/clock` arrive at full rate. Raw camera streams are heavy: the ZED depth image and point cloud (around 22 MB per message at 24-30 Hz) are much more than the TCP link can carry through Docker Desktop, so expect them at a reduced rate. To cap a topic's rate so it doesn't crowd out the rest, pass a flag such as `--pub-max-frequency '.*/point_cloud/.*=2'` after `native` or `docker` (extra arguments go straight to the bridge).

## Troubleshooting

- **Topics don't appear.**
  - Both bridges must run the same version. The image tag in `docker-compose.yml` and `VERSION` in `sim-bridge.sh` must match.
  - `ROS_DOMAIN_ID` must be the same in the sim, in the devcontainer, and in the environment you run `sim-bridge.sh` from.
- **`[sim-bridge] run this from a host terminal`.** You ran the script inside the devcontainer. Open a terminal on your machine instead.
- **The devcontainer or `up` fails on port 7447.** Another process is using the port. Check with `lsof -i :7447` (macOS/Linux) or `netstat -ano | findstr 7447` (Windows).
- **Native sim on an offline Mac.** With no network, CycloneDDS falls back to `lo0`, which has no multicast. Set `CYCLONEDDS_URI` to a config that uses `lo0` with multicast disabled and `127.0.0.1` as a peer. Export it in both the sim terminal and the `sim-bridge.sh native` terminal.
- **Sim container on Linux Docker Engine.** `host.docker.internal` doesn't exist there. Run the sim natively and use `native`, or point the bridge elsewhere with `ZENOH_ENDPOINT=tcp/<docker0 IP>:7447`. That second option also requires publishing the port beyond `127.0.0.1`.
